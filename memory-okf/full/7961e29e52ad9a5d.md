# CRITICAL: Rust daemon `set_var` does NOT reach the C core's `getenv` on Windows (ring + slab silently off)

**Proven 2026-06-30 via flushed DIAG in `gemma4_kv_open` (cuda_forward.cu).**

## The bug
The daemon maps `SP_DAEMON_KVDECODE_*` knobs to C-core env names via `std::env::set_var` in `daemon.rs`
(e.g. `SP_DAEMON_KVDECODE_RING_W` → `set_var("SP_G4_KV_RING_W")`, line ~610; my P3 slab loop ~623–637 →
`set_var("SP_ARM_SLAB")` etc.). **These `set_var` writes are INVISIBLE to the statically-linked CUDA
lib's C `getenv`.** On Windows the MSVCRT/UCRT `_environ` that `getenv` reads is snapshotted at process
(CRT) init and is NOT refreshed by Rust's runtime `SetEnvironmentVariableW`. So every set_var-after-start
knob silently no-ops in the C core.

## Proof (flushed DIAG, `gemma4_kv_open` hook)
- `run_console.bat` exact config (`SP_DAEMON_KVDECODE_RING_W=1024` knob): `getenv(SP_G4_KV_RING_W)=NULL  s->ring_W=0` → **SWA ring OFF**, no `[g4-kv] RING mode` line. Rust still logs "SWA-ring mode armed (1024)" — a lie vs the C core.
- Same for slab via knob (`SP_DAEMON_KVDECODE_SLAB`): `getenv(SP_ARM_SLAB)=NULL`, `g4_arm_open` never runs.
- Set the **C-level name DIRECTLY** as process env (`set SP_G4_KV_RING_W=1024` before launch): `getenv=1024  s->ring_W=1024`, `[g4-kv] RING mode: Wring=1024` fires → **ring ON**. Same for `SP_ARM_SLAB=1` → `g4_arm_open SUCCESS`, slab engages.

## Impact (the live system was mis-configured)
- The served 12B chat via `run_console.bat` has been running with the **SWA ring OFF** — full-cache globals AND full-cache SWA at Pmax=20000. The documented "O(1) SWA ring / VRAM-flat" behavior is NOT active through that launcher.
- `G-CHAT-B2-RING` ("ring-ON == ring-OFF token-identical") almost certainly compared **off == off** (both via the broken knob), so the real ring-ON behavior is **untested**. Re-gate needed.
- P2-A's VRAM ceiling (~24K) was measured **ring-off** (SWA full-cache) → real headroom with the ring actually on is larger.
- P3 corollary: the earlier "slab silent fallback / false green" was THIS bug, not a gather defect. With direct `SP_ARM_*` env, `g4_arm_open SUCCESS` + the gather RUNS: lossy `arm_B=1` → garbage divergence (proves it executes); resident `arm_B=256/Bslab=4096` → coherent on-topic output + recalls turn-6 "Saturn first" (correct, not bit-identical due to softmax-reorder vs full-cache).

## Fix
- IMMEDIATE: launchers set the **C-level names directly** as process env: `SP_G4_KV_RING_W`, `SP_G4_KV_JMAX`, and (P3) `SP_ARM_SLAB`/`SP_ARM_LSH_R`/`SP_ARM_BSLAB`/`SP_ARM_B`/`SP_ARM_SINK`. (`run_console.bat`, `run_console_recall.bat`, `run_console_nightshift.bat`, gate serve bats.)
- PROPER: refactor `daemon.rs` to pass ring_W / slab config to `gemma4_kv_open` by **function argument / setter**, not env — kills the set_var dependency entirely. The `SP_DAEMON_KVDECODE_*` knobs are unreliable by design on Windows.
- Audit ALL `std::env::set_var(...)` in daemon.rs feeding C `getenv` — every one is suspect.

Receipts: `_ringcheck.log` (knob → ring_W=0), `_ringfix.log` (direct → ring_W=1024 + RING mode), `_p33diag2.log` (direct slab → g4_arm_open SUCCESS + gather runs). DIAG instrumentation on branch `feat/okv-p3-global-evict` (cuda_forward.cu, uncommitted — strip or keep behind a flag before merge).
