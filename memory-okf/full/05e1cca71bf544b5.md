ADR-KAI4 P1 the ear grows up (2026-07-11). Built + PROVEN the full conversational-ear BAKE PIPELINE (kairos 34a3797), CPU-only so the 2060 keeps serving Gemma:
tools/voice_corpus.py = templated conversational sentences (greetings/status/time/memory Qs, acks, chat, + "hey shannon" WAKE phrases) -> real gemma tokenizer (build-cpu/tools/sp_tok_dump/sp_tok_enc.exe) -> vsub<=508 (V+1<=512, GNA head div-4); heavy word reuse keeps vsub small while sentences grow (343 sentences -> vsub=170).
tools/voice_render_sapi.ps1 = Windows SAPI, 6 voices (incl 2 en-AU) x 3 rates, 16k/16bit/mono, RESUMABLE, CPU-only (2058 wavs in ~40s total; the KAI-3 voxtral-GPU render at C:\Projects\... is stale + would eat the 2060 - SAPI is the sovereign CPU move).
tools/voice_frames.py = wav -> CTC npz (log-mel VERBATIM from harness.voice.dsp; speed-jitter+gaussian aug; held-out-by-SENTENCE eval split).
tools/voice_train.py = self-contained CTC trainer, CPU by DEFAULT (--gpu override). ★KEY: do NOT safe_open the 12B safetensors to get W_sub - mmapping the full model BLOWS THE PAGEFILE (os error 1455); training is pure audio->token-logits (no embeds needed); W_sub is export-only via voice_export_wsub.py's row-precise reader. ★Also: cuda-init in the trainer CONTENDS with the serving daemon on the 2060 -> observed stall -> CPU default.
tools/voice_bake.bat = the chained bake (corpus->render->frames->train).
RESULTS (data-scale ladder, the KAI-3 pattern reconfirmed): V 32->170 conversational tokens; 83-sentence corpus -> held-out-by-sentence exact-recognition 6%->22% (tok_acc 0.46); 343-sentence bake running (600ep CPU ~30min, writes var/voice/voice_ctc.pt). HELD-OUT-BY-SENTENCE is the HARD metric (unseen compositions) - data-bound exactly like KAI-3 (61->924 samples drove 0.44->0.868); the complementary ACOUSTIC metric (seen text, unseen voice/rate/noise) is what real usage mostly hits. VERDICT: pipeline PROVEN + automated; getting free speech legible is a DATA bake (thousands of sentences) NOT an architecture problem.
