# FAITHFUL-F1: in-context fact obedience baseline (G-FAITHFUL-BASELINE)

**Banked 2026-07-01. Engine main `fea18b3`. Harness `tests/perf/_g_faithful_baseline.py`; receipts `tests/fixtures/faithful/G-FAITHFUL-BASELINE.{log,json}`.**

## Result (served gemma4-12b-b1, 15 strong-prior fact-conflicts, temp=0)
- CONTROL (no context): **15/15 parametric-default (100%)** — every prior is strong, so the eval is valid.
- T_NEUTRAL (neutral system prompt + fact in context): **obey 14/15 = 93.3%** (the only leak is "capital of France" → Paris, the single strongest prior).
- T_CONSOLE (the current console "use facts you were given faithfully" prompt + fact in context): **obey 15/15 = 100%**, leak 0.

## The finding (reframes the Faithfulness campaign)
**In-context faithfulness is already ~solved.** The served model obeys an explicit in-context fact that contradicts its parametric prior **100%** of the time under the existing console system prompt (93% even with a neutral prompt). The feared "parametric leakage" is NOT an in-context (RAG/prompt) problem — do NOT spend effort "fixing" in-context obedience; it works.

## The real open gap (F1b, next)
The sharper question is the **RECALL-PATH delivery**: when the conflicting fact is stored as a MEM-OKF episode and injected via the W_c/replay seam (NOT as clean prompt text), is it obeyed as faithfully? The in-context baseline proves the model CAN obey context perfectly, so any recall-path faithfulness gap would be a MECHANISM (delivery) issue — the episode K/V replay or the text-in-context synthesis — not a model-obedience issue. F1b = store the fact-conflict items as episodes + auto_recall + measure obey vs the 100% in-context ceiling.
