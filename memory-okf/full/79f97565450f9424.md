# dg_self_cond OOB fix is LOAD-BEARING for diffusion-judge recall (CAUTION before re-fixing)

The dg_self_cond buffer OOB was real: the harness sized self-cond to canvas CL=16 but the forward writes C=256, so dg_k_softmax_rows (a vocab-space softmax over V=262144) over-read uninitialised memory. compute-sanitizer memcheck pinpointed it; fixed by zero-init dev alloc + sizing the harness buffer to the full model canvas. This was the root cause of the SP_DG_ASYNC non-determinism (the async machine itself was correct).

BUT: zeroing/correcting self-cond COLLAPSED the judge full-corpus recall (single-digit pct at STEPS=12 vs the prior 95.6 pct external oracle). The buggy self-cond garbage was LOAD-BEARING for the judge step-0 discrimination.

Before re-fixing self-cond, ADJUDICATE: is step-0 self-cond meant to be zero, or does discrimination require the full multi-step entropy-bound denoise (N3/N4 sampler depth; the 95.6 pct ran 48 steps)? This is why SP_DG_ASYNC default-on is HELD (async is byte-exact vs baseline either way -- this is judge-quality, not concurrency).
