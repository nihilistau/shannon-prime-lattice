N5b RESIDENT-WEIGHT RESERVOIR = NECESSARY-BUT-INSUFFICIENT. The design (DESIGN-diffgemma-n5b-reservoir.md) assumed the ~3 min/step diffusion-judge cost was the disk RE-FAULT of the mmap-aliased 26B weights, and that a one-time host-RAM reservoir would collapse it. MEASUREMENT REFUTES THAT PREMISE.

IMPLEMENTED: a per-tensor resident clone cache in cuda_forward.cu (dg_resident_pt / dg_reservoir_free, gated SP_DG_RESERVOIR, default-off = reads the mmap-aliased &at->pt exactly as before = byte-identical null floor). On first touch of an arena tensor it clones the packed buffers (codes/row_off/row_prec/row_scale/bscale) into owned committed heap once (faulting the mmap in a single time); every later access reads RAM. Builds GREEN.

ENGAGES (telemetry-confirmed): 143 [N5b] clone lines on one run - embed 369MB, big layer tensors 253MB x2, etc. So the reservoir is NOT a no-op; it really makes the weight SOURCE resident in host RAM.

BUT NO SPEEDUP: in the runaway A/B (reservoir ON), per-query time was FLAT across queries: q1=785s, q2=+743s, q3=+747s ... ~186s/step. Warm query (q2, cache hit, no clone, no disk) ~= cold query (q1, includes the clone). So the per-forward cost is unchanged by the reservoir.

ROOT CAUSE: the one-time clone (~14GB read) costs only ~7s (q1 785 vs q2 743 = ~42s of clone+overhead amortized once). The ~186s/STEP is the per-forward DEQUANT (14GB OK_Q4B -> 28GB f32 on CPU) + cudaMalloc + cudaMemcpy H2D (28GB f32 over PCIe) done for every weight every forward in dg_upload_arena_w/rows. The host reservoir removes the DISK read from the dequant source but leaves the dequant+upload untouched - and THAT is the wall. The diffusion judge is dequant+upload-bound (compute/PCIe), NOT disk-I/O-bound.

REAL LEVER (N5c, the actual fix): stop re-dequanting+re-uploading per forward. Either (a) upload the PACKED OK_Q4B (14GB) to VRAM once + dequant in a GPU kernel per forward (cuts the 28GB f32 H2D to a 14GB one-time packed upload; but 14GB packed still > 12GB VRAM so needs partial-resident + LRU), or (b) a VRAM hot-expert LRU cache (design escalation b) keeping the most-used dequanted experts on GPU. The host-RAM reservoir is kept as a building block (default-off, byte-identical) but is NOT the speed fix on its own.

HARNESS BUG: test_diffjudge_denoise ignores SP_DJ_LIMIT/SP_DJ_FLIMIT (printed "needles=90 foreign=50" both runs = full corpus) -> two runaway multi-hour bakes were killed. A tight N5b A/B needs a real per-query limit or a single-forward micro-harness + per-step cudaEvent timing.

STATUS: cuda_forward.cu reservoir change BUILDS GREEN, default-off null floor, byte-identical-by-construction, but UNCOMMITTED (honest negative - doesn't deliver the speedup it was built for; keep or redirect to N5c is the operator's call).
