# RESOLVED: set_var config-bus torn out -> explicit KvOpenCfg (ring/slab now engage via the knobs)

**Fix for the RED finding (banked 7961e29): Rust daemon `set_var` does not reach the static CUDA lib's
C `getenv` on Windows.** Engine commit `0478345` on `feat/okv-p3-global-evict`.

## What changed (structurally sound — no env bus between Rust and C)
- **cuda_forward.cu:** a file-scope config bus `g_g4_open_cfg` + `gemma4_kv_set_open_cfg(ring_w,jmax,arm_slab,arm_bslab,arm_b,arm_sink,lsh_r)` / `gemma4_kv_clear_open_cfg()`. `gemma4_kv_open` now resolves ring_W/Jmax + the slab decision + `g4_arm_open`'s Bslab/B/sink/LSH-path from the cfg when `.set`, else falls back to `getenv` (standalone test bins unchanged).
- **glue (sp_daemon_cuda_glue.c):** `sp_daemon_cuda_kvdecode_open_cfg(qm,pmax,ints…,lsh_r)` = set cfg → `gemma4_kv_open` (consumes it) → clear. The existing `_open` (env) kept.
- **cuda_kvdecode_dispatch.rs:** `KvOpenCfg{ring_w,jmax,arm_slab,arm_bslab,arm_b,arm_sink,lsh_r}` + `KvOpenCfg::from_env()` (reads the `SP_DAEMON_KVDECODE_*` knobs OR the direct `SP_G4_KV_*`/`SP_ARM_*` names — all in Rust, which works) + `open_cfg()`; `register_with_session(…, &cfg)`.
- **daemon.rs:** builds the cfg from env in Rust + passes it; **ALL `set_var` removed**. `sp_wire_cuda_decode_gate.rs` caller updated to `&KvOpenCfg::from_env()`.

## Proof
- Knob `SP_DAEMON_KVDECODE_RING_W=1024` (the `run_console.bat` config) now logs `cfg (explicit, no set_var): ring_w=1024` AND fires the C line `[g4-kv] RING mode: Wring=1024` — i.e. the ring **engages** (it was `ring_W=0` / silently off before).
- **G-CHAT-B2-RING re-gate GREEN (first REAL ring-on test):** 6-turn chat with the ring genuinely engaged is **byte-identical to the ring-off baseline** (SHAs f3c73fe8…→fd99510b…), coherent, and persist-O(1) TTFT stays flat (~1s). The original B2-RING compared off==off (both silently off), so this is the first true validation.

## Operational
- `run_console.bat` / `run_console_recall.bat` / `run_console_nightshift.bat` need **NO change** — their existing `SP_DAEMON_KVDECODE_RING_W` knob now actually engages the ring through the explicit bridge. (Previously the live served chat ran SWA-ring-OFF: full-cache globals AND SWA.)
- P3 slab flows through the same cfg (`arm_slab/lsh_r/bslab/arm_b/arm_sink`), so the P3.3 gather (proven to run + be coherent via direct env) now also arms via the daemon knobs.
- Test bins (`test_gemma4_cuda.c`, `eagle_accept`) unchanged — `.set==0` → getenv fallback.
