# TELE-15: cemented two-stage Telepathy delegate is LIVE (G-TELEPATHY-LIVE GREEN)

**Banked 2026-07-01. Branch `feat/telepathy-v1`, engine commits `c3c4b22` + `ef6c282`.**

## What is now built (do NOT rebuild)
- `telepathy.rs::delegate_execute(task_text, bridge_id)` is now **REAL** (was a stub returning "WIRING PENDING"). It loads the qwen coder sp-model (`SP_TELEPATHY_DELEGATE` + `SP_TELEPATHY_DELEGATE_TOK`) and decodes the CLEAN-TEXT task **token-in via CPU L1** (`SpSession::prefill_chunk` / `decode_step`), returns the answer string. Reuses the proven `run_telepathy_native` pattern.
- New verb `telepathy.rs::run_telepathy_live()` + dispatch `SP_TELEPATHY_LIVE=1` in `main.rs` (one-shot, before Cli::parse, like SP_TELEPATHY): stage 1 `decide_route(latent)` → stage 2 `delegate_execute(clean text)`.
- Launcher `tools/sp_daemon/_telepathy_live_run.bat` (env-cuda + SP_TELEPATHY_LIVE=1 + SP_ROUTE_FORCE=1 + delegate model). Build `tools/sp_daemon/_telepathy_build.bat`.

## Gate
**G-TELEPATHY-LIVE GREEN** (receipt `tests/fixtures/telepathy/G-TELEPATHY-LIVE.log`): route `Telepathy(1)` → qwen coder decoded 24 toks (29.8s, 0.8 tok/s, CPU L1) → coherent on-task answer ("Here's a Python function that reverses a string: ```python def reverse_string...").

## Hard architectural rules (from TELE-12, enforced here)
- **NEVER fuse latent prefix + text** in one delegate forward — that is the measured 0.000 honest-negative. The latent's ONLY job is the route decision (stage 1, gist/intent). Stage 2 is CLEAN TEXT.
- The literal "inject the mapped latent to override Qwen's token embeddings" path is NOT buildable as v1: the frozen L1 ABI (`sp_l1.h`) has only `sp_prefill_chunk(tokens)` + `sp_decode_step(token)` — there is NO inputs_embeds prefill verb; `gemma4_kv_inject_seq` is a CUDA gemma4-cache verb, not the CPU L1 qwen session. Building that seam would re-implement the refuted fuse. DON'T.
- GPU-speed qwen transmit is blocked by the arch gap: CUDA `qwen3_decode_cuda` is `SP_ARCH_QWEN3`-only (rejects the QWEN25 coder); `qwen3_generate_kv` segfaults on the CUDA session. The qwen coder runs ONLY on CPU L1 (~0.8 tok/s). v1 = CPU path by design.

(Currently the LIVE gate is the standalone one-shot verb.)
- GPU-speed would require fixing the qwen CUDA arch gap (separate, larger).
