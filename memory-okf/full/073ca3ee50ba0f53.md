# TELE-16: two-stage Telepathy delegate wired into the LIVE /v1/chat (G-TELEPATHY-CHAT-LIVE GREEN)

**Banked 2026-07-01. Branch `main`, engine commit `50200eb` (on top of telepathy-v1 tag `02bd0ae`).**

## What is now built (do NOT rebuild)
- `routes.rs::run_kvdecode_chat` has a **served Telepathy splice** gated `SP_TELEPATHY_CHAT=1` (default-off = byte-identical null floor), placed **BEFORE the GPU cache guard** so a delegated turn never touches the Gemma resident cache.
- On a TELEPATHY route → emits `SP_TELEPATHY_MARKER` delimiter (default on: `⟦delegate: qwen2.5-coder⟧` … `⟦/delegate⟧`) → `telepathy::delegate_execute(raw_user, bid)` runs the qwen coder on CLEAN TEXT (CPU L1) → streams the answer into the live SSE `{delta}` stream → `[DONE]`.
- **Flag is DISTINCT from `SP_TELEPATHY`** (which is the one-shot parity verb in main.rs that early-exits before serving — reusing it would make the daemon exit instead of serve; caught + avoided).
- Launchers (scratch, `_`-prefixed, gitignored): `_telepathy_serve.bat` (12B daemon + the telepathy env, uses `start` to DETACH so it survives across calls), `_telepathy_chat_post.bat` (curl POST).

## Operational notes / traps banked
- The daemon launched via `--daemon-inner` as a child of the MCP shell call DIES when that call ends (process-tree cleanup). Use the `start` subcommand (DETACHED_PROCESS) to keep it alive across poll calls. `start` does NOT redirect the inner's stdout, so poll the PORT (fast TcpClient), not a log.
- `Start-Process -ArgumentList` mangles curl `-H "Content-Type: application/json"` (space-splitting) → daemon rejects with "Expected request with Content-Type: application/json". Use a `.bat` with the curl line for reliable quoting.
- Live delegate latency: ~10s qwen load + ~16 toks @0.8 tok/s ≈ 30s/turn. CPU path by design (GPU qwen blocked by SP_ARCH_QWEN3 gap).
