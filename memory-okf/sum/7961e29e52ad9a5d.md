# CRITICAL: Rust daemon set_var does NOT reach C getenv on Windows -> SWA ring + P3 slab SILENTLY OFF via the SP_DAEMON_KVDECODE_* knobs

PROVEN (flushed DIAG in gemma4_kv_open): daemon.rs std::env::set_var(SP_G4_KV_RING_W / SP_ARM_SLAB / ...) is INVISIBLE to the statically-linked CUDA lib's C getenv (Windows MSVCRT _environ snapshotted at process init, not refreshed by SetEnvironmentVariableW). run_console.bat knob SP_DAEMON_KVDECODE_RING_W=1024 -> getenv(SP_G4_KV_RING_W)=NULL, s->ring_W=0 = RING OFF (Rust logs 'ring armed' = false). Direct process env 'set SP_G4_KV_RING_W=1024' -> s->ring_W=1024, [g4-kv] RING mode fires = ON. Same for slab (knob NULL; direct SP_ARM_SLAB=1 -> g4_arm_open SUCCESS, gather runs). IMPACT: live served chat ran SWA-ring-OFF (full-cache globals+SWA @Pmax20000); G-CHAT-B2-RING likely compared off==off (real ring-on untested); P2-A ceiling measured ring-off. P3.3 gather IS validated via direct env (lossy arm_B=1 garbage divergence; resident arm_B=256 coherent + recalls). FIX: launchers set C-level names DIRECTLY (SP_G4_KV_RING_W/JMAX, SP_ARM_*); proper fix = daemon passes config to gemma4_kv_open by ARG not env. Audit all set_var->getenv in daemon.rs.
