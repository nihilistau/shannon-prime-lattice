## 2. THE finding — the launchers do not run the verified edge

The faithfulness axis is CLOSED (SCOREBOARD: `SP_RECALL_L5` 86.89% + `SP_RECALL_ATTR_GATE` zero-inference decline). But **no launcher in the engine repo sets `SP_RECALL_L5`, `SP_RECALL_ATTR_GATE`, or `SP_RECALL_JACCARD`** (`grep -l SP_RECALL_L5 *.bat` = empty):

- `run_console_recall.bat` still drives the **superseded W_c selector** (`SP_B3_WC` + `_needle_corpus_div` registry) — the 2026-06-19 edge, not the 2026-07-01 edge.
- `run_console_nightshift.bat` also W_c-based, and inconsistently drops `SP_PERSIST_KV`/`SP_EOT_BIAS` that `run_console.bat` sets.
- The verified L5 gates were run via inline env / harness scripts only. **An operator following the repo's own quickstart boots the old brain.**

The recall pipeline in `routes.rs` is a staged chain — INT2 → B3-WC → Jaccard → L5 → judge — each stage gated on "no prior stage decided" (`routes.rs:1258,1346,1412,1517`). So W_c+L5 can legally coexist (W_c NULL falls through to L5), but that combined config has **no gate receipt**. Resolution + the canonical config: **`RUNBOOK-ONE-CONFIG.md`**.

## 3. Reproducibility hole — 3.3GB of load-bearing artifacts untracked

`.gitignore:133` blanket-ignores `_*/`. Consequence (verified via `git ls-files`):

If the disk dies, the verified live-recall state is **not reconstructable from the remotes**. Mitigations, cheapest first: (a) track the small load-bearing files now (wc_deploy.bin 64K, registries, facts.json, ep.l5 2K×61, ep.mf) — trivial; (b) the heavy ep.k/ep.v are *derivable*: byte-exact capture from facts.json + the model should reproduce them bit-identically (`SP_BYTEEXACT` is the whole point) — one gate (`G-EP-REBUILD-BYTEEXACT`) would prove the corpus is regenerable and make tracking the KV unnecessary; (c) bank the artifacts into MEM-OKF (content-addressed) so SP-SWARM replicates them across nodes — this is literally the mesh's designed job.
